# 《示例数据校验报告（v1）》处理说明

对应报告：示例数据校验报告 v1（2026-11-16）。下表逐条说明：问题原因、工具侧怎么改的、还需要谁做什么。
「已改」= 工具逻辑已调整，重新生成 / 导出即生效（已生成的旧数据不会自动变，需要重跑或按新格式导出）。

## T2 智能客服对话

| 编号 | 原因 | 处理 |
|---|---|---|
| P0-1 source 带答案侧字段 | 我们导出的是内部全量文件（L1 + source） | **已改**：导出分两份，用同一个 session_id 关联。① **标注交付 L1**：session_id / channel / visitor_id / scenic_id / scenic_name / start_time / related_order_id / turns / session_duration_sec；② **溯源 sidecar**：source 全量 + end_type + satisfaction_score。页面「导出数据」默认就是 L1；批次文件也有这两个下载。 |
| P0-2（1）指代 / 省略样本缺失 | 生成时没有要求 | **已改**：程序事先给约 21% 的会话定「指代 / 省略」（其中 1/3 要求跨 3 条以上），模型须在 coref 里标出所在消息和被指消息，程序核对；没做到的标需复核。 |
| P0-2（2）订单号不在用户正文 | 订单号是程序事后补的，没让游客说 | **已改**：带订单的会话先生成订单号 / 票种 / 张数 / 游玩日期，要求游客在消息里明确说出、客服复述；游客没说出订单号的标需复核。 |
| P1-1 政策类、办理类 0 条 | 景区表没有退改 / 实名规则，原主题里没有这两类 | **已改**：新增主题「票务政策」（退改、实名、门票包含范围、优惠证件）和「订单办理」（退票、改期、改签、查订单、订单异常，均带订单号）。景区表里没有具体规则，所以资料里写明「未收录」，客服只能引导到订单页说明或提交申请 / 转人工，**不编规则**。如果有景区真实退改规则表，接进来就能给出具体规则。 |
| P1-2 end_type / 满意度失真 | 由模型自己选，偏向「用户主动结束 + 5 分」 | **已改**：由程序按分布先定：用户主动结束 45 / 客服结束 15 / 超时自动结束 15 / 静默离开 10 / 转人工后结束 10 / 用户不满中断 5；满意度约 35% 未评，已评中 5 分 25%、4 分 35%、3 分 25%、2 分 9%、1 分 6%；is_resolved 与结束方式一致（不满中断、转人工为未解决）。模型按这个写对话内容。 |
| P1-3 大观园地址 / 淡季开门时间错 | **客户景区表源数据错**（地址「南菜园西街」与简介「南菜园街」不一致） | **已改（拦截）**：生成前检查同一景区「地址」与「简介」里的路名、门牌，不一致的地址字段不用；票价倒挂、淡季高于旺季同样不用。全表查出 14 处地址不一致、276 处票价倒挂、9 处淡季高于旺季，可在页面下载清单（/api/cs/fact_conflicts.csv）。**淡季开门时间这类无法从表内自检，需要数据负责人修正源表。** |
| P1-4 神泉峡淡季 25 元倒挂 | **客户景区表源数据错**（淡季成人票 25 < 优惠票 28） | 同上，已拦截并列入清单；源表需修正。 |
| P1-5 start_time 晚于文件生成日 | 会话日期在 2026 全年随机 | **已改**：会话日期限定在「截止日前一天」之前（默认今天，可用 CS_DATE_END 指定），最多往前一年。 |
| P2-1 轮次模板化 | 提示词写死 4～10 条 | **已改**：条数按 3～20 的长尾分布事先定，偏差超过 2 条标需复核。 |
| P2-2 景区集中 | 按景区逐个出完所有主题 | **已改**：轮流排，先每个景区各 1 条再各第 2 条，前 N 条覆盖 N 个景区。 |
| P2-3 无语音 / 错别字 / 无标点 | 没有要求 | **已改**：约 8% 会话含 1～2 条游客语音（msg_type = voice，转写口语无标点）、5% 带错别字 / 同音字、5% 游客不打标点。 |
| P2-4 事实快照晚于会话日 | 同 P1-5 | **已改**：会话日期不早于景区资料更新日（update_time）次日；讲解类不早于知识库版本日。 |
| P2-5 复读残留 | 模型退化 | **已改**：检测同一条消息里 4 字以上的重复片段，标需复核。 |
| P2-6 首轮是机器人 | 提示词允许机器人先致辞 | **已改，按规定**：首条必须是游客；模型若以客服开头，程序去掉开头的客服消息并在 sidecar 记录。 |

## T3 讲解内容评价

| 编号 | 处理 |

| P1-1 缺讲解发生时间 | **已改**：guide_clip 增加 collect_time，程序保证晚于 kb_version（也晚于景区资料更新日），不晚于截止日前一天。请手册 5.2.1 同步补字段。 |
| P1-2 错误配比只覆盖 3 类 | **已改**：单点数值偏差 40% / 多点事实错误 25% / 完全正确 15% / 合规违规 10%（硬推销、绝对化、低俗调侃、缺安全提示）/ 逻辑问题 10%（时间线倒置、前后矛盾）；另约 12% 低置信度（0.45～0.69）拒答样本，标准答案为「拒答」。数值偏差要求超出 2% 容差，2% 以内视为正确。 |

| P2-3 同一 POI | **已改**：轮流排，一批覆盖不同景区、不同知识条目。 |
| 其他 | kb_entry.facts 不足 6 条的用所属景区真实资料补到 6 条（最多 10）；gaps 1～3；时长 ≈ 4.5 字/秒、不短于 20 秒；语气词密度按来源检查（录音笔 ≥4 / 直播 ≥3 / 短视频 ≥2 处每 100 字）。 |

## T1 景点图像识别

| 编号 | 处理 |
|---|---|
| travel_date | 它是交付表 ods_prd_poi_image_di 的**分区字段**（建表时就有），表里不能删；**已改**：新增交付导出（图片预览页「交付导出」），只出手册字段，不含 travel_date。 |
| P1-1 total_count 对不上 | **原因已查明**：页面拿不到图片总数时，程序会从页面文字里找「N张图片」，可能把某条点评的图片数当成 POI 总数。**已改**：去掉这类易误抓的规则；每个 POI 采完把 total_count 校正为不小于已采张数；历史数据启动时一次性校正。口径：POI 图片总量（携程页面上的总数，拿不到或偏小时取已采张数）。 |
| P1-2 / P2-4 单 POI、条数 | **已确认按真实数据**：体量已够，不按合成约束截断（每个 POI 不再限 8 张）；交付导出按 POI 分组、多 POI，可按城市筛选。 |
| 量级与景区强对应（新要求） | **已改**：交付导出只含「景区已审核（approval=1）且该 POI 仍在它的保留列表里」的图片；核对后被取消的 POI、未审核景区的图片都不出。导出前可看量级（景区数 / POI 数 / 张数 / 因未确认被排除的张数）：/api/images/delivery/stats。 |
| P2-1 脏数据率 0% | **已确认按真实数据**，不往真实数据里人为注入脏数据。 |
| P2-2 无夜景难例 | 采集时间是我们的采集时间，不是拍摄时间，无法体现夜景；难例需按图片内容另行标注。 |
| P2-3 W_640 与 width | image_url 里的 W_640 是携程缩略图规格，width / height 是原图尺寸，两者不是一回事；建议手册 3.2.1 加备注。 |
