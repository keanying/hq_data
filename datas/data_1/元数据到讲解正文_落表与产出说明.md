# 从来源元数据到讲解正文

用户真正需要的交付是带景区身份与来源证据的内容记录。topic、guide_title、guide_text、original_excerpt和excerpt_source_url是首批CSV的五个核心内容字段。其中guide_text是依据已读取资料整理的介绍，original_excerpt才是网页原文必要短摘录；不能将两者都叫原文抓取结果。

## 五个核心字段的落点

- topic → 内容主表guide_topic_name。
- guide_title → 内容主表guide_title_name。
- guide_text → 内容主表guide_content_text。
- original_excerpt → 内容主表original_excerpt_text。
- excerpt_source_url → 内容主表excerpt_source_id关联来源页面表source_id取得source_url；并按collect_batch_id和travel_date限定同一批次。

业务粒度为一个景区或子景点的一个讲解主题一条内容，不是一个官网首页一条内容，也不是一个元数据URL自动生成一条讲解。相同景点的历史与建筑可分别成条，前提是内容独立且有证据。

## 六张表分别记录什么

1. dwd.dwd_prd_scenic_guide_content_di记录景区和景点身份、主题、标题、正文、摘录、范围及内容类型。本演示80行。
2. dwd.dwd_prd_scenic_guide_fact_di记录正文依据的细粒度事实，一个事实一行。本演示395行。
3. dwd.dwd_prd_scenic_guide_source_di记录实际读取并用于内容的页面及发布机构，不把所有候选链接直接当成有效来源。本演示77行。
4. dwd.dwd_prd_scenic_guide_content_source_rel_di记录每条内容用了哪些来源，标出哪一个支持原文摘录。本演示133行。
5. dwd.dwd_prd_scenic_guide_fact_source_rel_di记录每条事实由哪个页面支持，一条事实可有多来源。本演示436行。
6. dwd.dwd_prd_scenic_guide_collect_task_di记录该批次该景区的正文采集结果和实际产出数量。本演示20行。

六表用collect_batch_id、travel_date及各自的content_id/source_id/fact_seq_no关联。来源去重粒度按现有设计保留景区来源ID；一个URL在不同景区可能对应不同source_id。

## 正文采集的执行顺序

第一步，筛选元数据候选。source_access_status=1只是标题或简介可读，不能当成正文成功。优先处理已确认来源、官网的景点介绍与历史文化栏目，再用政府、文物机构资料补充。携程优先用作景点定位和公开介绍线索，使用时明确OTA来源，不冒称官方知识库。

第二步，核验景区身份并深入文章页。核对名称、城市、地址及页面主题，避免同名景点、公司集团首页、相邻景区或遗产组成点误配。打开景点专文或栏目下的文章，提取正文主体，排除导航、门票营销、游客点评、页脚和与景点无关的新闻。不能仅采HTML的head、页面标题或meta description，也不能截断页面后就宣布正文完整。

第三步，保存本次正文证据。记录实际文章URL、正文读取时间、正文片段和文本哈希，在ODS原始采集层或有访问控制的对象存储中保存可回溯证据。现有六张DWD表不保存完整原始网页或原始文章全文；仅有source_evidence_flag不足以重放正文处理。采集证据的存档位置和哈希需要额外的原始层记录或新增字段，属于建议补充，不是已经建好的第七张表。遵守robots和访问限制，不绕过验证码或付费门槛。

第四步，按景点和主题提取事实。每个日期、结构、数值及文物属性都对应实际正文支持片段。跨来源冲突保留限定或暂不采用，不把所有数字都当成同一口径。来源无支持就不补造；不要求给每个景点强行填固定条数。

第五步，形成核心内容。topic和guide_title可从文章主题规范化；original_excerpt必须来自实际读取页面的连续必要短摘录，并与excerpt_source_url一致。guide_text可在有证据的事实基础上整理为可读中文介绍，但必须标guide_content_type=1。若实际获得了可再利用的逐字讲解词才标2；若实际获得有权限处理的音频并转写才标3。本批没有模拟录音、模拟ASR或事实错误注入。

第六步，检查后落表。检查景点边界、正文来源支持、摘录连续性、重复内容及POI编码来源。不把旧元数据读取时间当成本次正文读取时间。任务表中的正文数量和事实数量从对应表汇总，不拿链接数量替代内容产出。

## 现有DDL需要适配的地方

现有source_type枚举仅1至5，未覆盖OTA。本次演示仍使用首批已采集的官方、政府和文物资料，不改动原DDL。未来纳入携程公开介绍时，应先扩展source_type为6-OTA平台并同步CHECK约束；不能硬映射为5-其他权威来源。

无法确认发布机构的候选应留在原始/候选层，待核验后进入当前来源表；若业务确实允许未知发布机构进入DWD，应先将source_publisher_name改为可空，并[dwd_prd_scenic_guide_content_di.csv](dwd_prd_scenic_guide_content_di.csv)增加明确的来源核验状态。不要用编造的机构名称填NOT NULL字段。

metadata中的metadata_id不是直接可复用的source_id；正文采集应建立metadata_id/source_url到内容批次source_id的映射。元数据候选、实际正文来源和成功内容是三个不同状态，不能一次全量导入六表后都标成功。

## 怎样产出业务CSV

《核心讲解内容导出_mysql8.sql》只连接内容主表与摘录来源表，还原五个核心字段和景区身份。主表每条内容只对应一个excerpt_source_id，所以不会因多来源或多事实造成行数膨胀。本次用本地数据映射还原的《六表还原_核心讲解内容.csv》有80行，五个字段与首批CSV逐字一致；这是本地校验，不是声称数据库已执行SQL。

需要全部来源时，将内容来源关系先按content_id聚合为数组后关联；需要facts_json时，将事实及其来源先按事实和内容聚合。不要把两张一对多明细同时直接展开JOIN，否则一条内容会重复为多行。

## 演示文件的边界

六张CSV已经按原DDL列名排列，省略ingest_time，使真正导入时由数据库在UTC会话下产生实际入库时间。可空字段的CSV空字符串由导入程序转NULL，特别是来源发布日期与未匹配POI。示例collect_batch_id为scenic_web_20261112_first20，是建议导入批次参数，不代表用户数据库已存在该批次。

这份演示只将既有20景区80条内容规范化为六表，没有重新联网采集，没有新增景区内容，也没有启动新的全量正文任务。全量元数据中已取得候选页面元数据的8577个景区仍需依照上述正文流程逐一处理；7992个无来源景区仍需独立检索，另有598个有来源但本轮未取得有效元数据的景区需要补查。主档105786个景点名称只是线索，不代表具有同等数量的真实讲解内容。
